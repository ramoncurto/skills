# Director-owned swarm and release

Discover repository rules, package/runtime versions, required checks, provider tools and release conventions. Do not import project-specific commands, locale counts, domains, app IDs or deadlines from previous runs. If another relevant skill is installed, read it once and reuse its contract rather than copying its entire implementation.

## Isolate first

Record the current branch/base, staged/unstaged/untracked WIP and other active worktrees. Use a separate checkout when unrelated or concurrent WIP would contaminate the candidate. Preserve a reconciliation receipt when an agent wrote into the wrong cwd; only restore bytes proven to be owned by that agent and initially clean. Never clean another task's branch, force-reset dirty main, or stash ongoing work blindly.

## Atom brief

Use only independent workstreams that save time or improve confidence. Each agent receives:

- Exact absolute checkout and owned paths; explicitly prohibit the other checkout.
- One concrete behavior/defect and the director's decisions, including intentional exclusions.
- Before/after acceptance evidence and the appropriate focused checks.
- A clear boundary for auth, DNS, content policy, dependencies and public contracts.
- An artifact path outside shared source when returning read-only evidence.
- A stop condition and handoff; no commits, provider actions or overlapping edits unless specifically assigned.

For example, separate canonical hub links, shared lesson navigation, sitemap dates, breadcrumb JSON-LD, robots parsing, locale metadata and read-only content inspection. These are examples, not a mandatory seven-agent fan-out. Batch by actual ownership and the repository's caps. Let the director handle dependent integration and irreversible decisions. Do not spawn more agents just to obtain a nicer review verdict.

## Evidence layers

Keep these distinct in the run record:

1. Source/config and deterministic tests.
2. Public HTTP response, canonical, robots, status and native HTML.
3. Real browser behavior, rendering and user journey.
4. Owner/search-engine/scanner observation with its report date.
5. Measured post-change indexing, traffic, approval or business outcome.

Inspect content and source behavior before making a quality claim. Preserve the actual failed baseline and reviewer findings, including rejected findings with a concrete reason. Match verification breadth to the change; do not repeatedly run tests that cannot resolve a new concern.

## Freeze, review, release

Finish all bundle edits, including worklogs, before a review tool that validates the entire working tree. Record the reviewed paths/revision or hashes. A full-tree review invalidated by a concurrent document edit is not a clean review. Source hashes can still establish the narrower validity of prior tests; say exactly which layer remains valid.

Independently review substantive code changes. Accept only verified in-scope findings, fix the affected bug class within its owner boundary, and rerun relevant checks/review. Avoid scope drift from speculative findings. Metadata/copy changes can require a truthful new sitemap date for that page while unchanged siblings keep theirs.

Complete the user's already-authorized lifecycle: commit → push → PR → required CI → merge → production deployment → served/browser/provider acceptance → task branch cleanup. Do not stop at a local build or preview deployment when production release was requested. Do not broaden a fixes-only task into billing changes, auth redesign or outreach without applicable authority.

Use one coherent ordered ledger: local fixes/checks → independent review → authorized commit/PR/CI/merge/deploy → production readback → provider submissions → cleanup/receipt. Do not put production verification before its release, or repeat the release after provider actions. A future DNS/provider wait must not delay independent fixes, the safe release, or other eligible current actions.

Tie production to the actual revision using provider deployment metadata or a verified commit-status/deployment/alias chain. Recheck the changed pages and representative siblings on production. Preserve remaining intentional warnings and distinguish a heuristic warning from a failed contract.

Advance main and remove only the task branch/worktree after verifying ancestry and preserving unrelated WIP. If local documents overlap, reconcile their entries with explicit before/after evidence; never drop another task's log. Record any preservation blocker rather than saying cleanup succeeded.

## Final receipt

State the concrete result early. Include the release/revision, meaningful verification, actual scanner score and provider state, bounded content findings, unresolved conditions and one next action per external wait. Keep the user-facing answer concise and link the full evidence record. No “fully fixed” claim when the requested external outcome remains unobserved.
