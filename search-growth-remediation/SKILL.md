# Search Growth Remediation

## When to use

Use for a project recovery pass involving GSC exclusions, AdSense content/site readiness, or an AgentReady score target. A request to apply or run this remediation skill means diagnose and fix the requested tracks, beginning with read-only evidence collection. For an explicit audit/plan-only request, deliver the evidence and actionable plan without executing mutations; that requested deliverable can be complete while remediation remains unstarted. The shared discipline is evidence → bounded fixes → verified release → provider readback.

A high AgentReady score does not establish Google quality, indexing, ranking or AdSense approval. Treat these as separate outcomes throughout the run.

**Completion contract:** In remediation mode, continue until every required finding is fixed and verified and every explicit target is met. A successful batch, merged PR, deployed improvement, documented backlog or increased score is a checkpoint, not completion. Keep the requested scope and targets fixed unless the user changes them; do not silently reduce them to the easiest available fixes.

## Steps

1. **Recover context and authority.** Read the project instructions, latest worklog, previous receipts and existing session authorizations. Discover the real production domain, canonical host, stack, locales, provider accounts and release path; do not transplant another project's IDs, dates or settings. Preserve existing approval instead of asking again. Determine authority from the user's request and session context; do not downgrade a remediation request to diagnosis-only or infer new external-action permissions from the skill itself. Carry authorized fixes and releases to completion.
2. **Establish the current state and finish line.** Read the actual owner property and current scanner profile, not only screenshots or remembered numbers. Record the requested deliverable, score/outcome targets, profile, report dates, URLs, cohort denominators, source evidence and unknowns. Recheck drift-prone facts against official documentation. Copy [assets/run-record.json](assets/run-record.json) into the project's normal evidence location and fill only observed fields, leaving unknowns null. Set templateOnly to false only for an actual captured run; template values are not observations.
3. **Route the requested tracks.** Read [references/gsc.md](references/gsc.md) for indexing/crawl findings, [references/adsense.md](references/adsense.md) for content/site rejection work, [references/agentready.md](references/agentready.md) for the scanner's concrete failed checks, and [references/semrush.md](references/semrush.md) when competitive, keyword-gap or country/language demand research is requested. Keep separate finding queues and provider outcomes even when one fix benefits several tracks.
4. **Account for every finding.** Classify each finding as an owned defect, intended exclusion, inapplicable capability, stale observation, or external pending decision. Confirm applicability from evidence. A capability missing today is not automatically out of scope when it is needed for the requested target: design and implement useful supported behavior within authority, or identify the exact scope/authority decision required. Preserve unresolved failures in the scoreboard; do not hide checks, invent endpoints, pad content, or call a local pass an external success. An inapplicability label does not satisfy an unmet explicit score target.
5. **Plan atomized work.** Read [references/release-and-swarm.md](references/release-and-swarm.md). Direct independent, disjoint tasks with explicit files, behavior, acceptance and stop conditions. Default independent bounded executors to an available Luna model (currently `gpt-5.6-luna` when advertised), unless the user explicitly chooses another model. If Luna is unavailable, disclose that, do small bounded work locally, and choose or escalate only a concrete difficult atom when warranted and allowed; do not launch an automatic replacement swarm or invent a model ID. Retain director ownership of integration, security/privacy decisions, review, release and provider actions.
6. **Implement and verify.** Reproduce concrete defects, make the smallest useful changes, and run meaningful focused regressions plus the project's required gate. Compare representative served HTML and real browser behavior. Add newly discovered required defects to the same queue. Use existing SEO/audit/review skills when installed and applicable; the references here also describe the standalone workflow. Do not install tools, start trials, spend money or change unrelated product scope merely to improve a score.
7. **Freeze and release.** Finish evidence-document edits before starting a review that hashes the working tree. Record exact source identity, review findings and fixes. Complete the already-authorized push/PR/CI/merge/deploy/cleanup path, preserving unrelated WIP. Verify the production alias and source revision, then retest the deployed behavior; local and preview checks are not production acceptance.
8. **Perform eligible provider follow-through.** Reuse valid session authorization for the concrete action. Submit only appropriate limited indexing/review/recrawl actions after prerequisites pass, and read back the queue/provider state. Do not repeat requests to force a result, restart an existing validation, bypass quotas, or send support/outreach messages without message authorization. If a genuinely missing approval remains, prepare the concrete action and evidence first, then ask once and explain its source.
9. **Rescan, reopen and repeat.** Compare fresh production/provider results against the original finish line and every queued finding. If any required fix is still actionable, return to steps 4–8 and continue in this run. Do not finish merely because one release passed, the score improved, a batch/time estimate ended, or remaining work is harder. Continue all independent authorized work while another item waits. A real external dependency or missing authority can block the overall result only after no authorized work can advance it: record evidence, attempted safe remedies, owner, exact next condition/action and safe timing, and report the task as incomplete. Schedule later work only when requested. Close successfully only when the Done when conditions all hold.

## Done when

For diagnosis/plan-only mode, finish when the evidence, priorities, concrete proposed fixes, validation and authority requirements are delivered. The conditions below apply to an authorized remediation run, not to a plan-only deliverable.

- Every required finding is corrected and verified at the required layer; no actionable required defect remains. Evidence-backed intended exclusions may be retained, but cannot waive an explicit target.
- Required review/tests and the authorized release/provider lifecycle are complete; unrelated work is preserved.
- The scanner's requested score is verified from the same live profile and its real score field. If unavailable or still below target, report that exact limit rather than a synthesized 10/10.
- GSC queue acceptance, crawl/index state, measured impressions and the AdSense decision remain separately labelled. “Review requested” is pending, not approval; a sampled content pass does not clear an entire site's low-value verdict.

A blocker receipt is not a successful remediation result. Keep `requestedOverallOutcome` incomplete and any overall `doneSignalMet` false while required findings, verification or explicit targets remain unresolved. Individual stages may pass; their success must not be substituted for the overall finish line. Provider decisions and measured outcomes need only be achieved when explicitly requested, but must never be claimed from readiness fixes alone.
